## 1. 一句话架构

**把原版的「五个进程内外来回倒腾」压成「一趟内存里的流水线」。**

原版（每一步都要把数据完整落地一次）：

```
X ──pp──> X' ──L2归一化──> 写 .ijv 文本文件 (11.4s)
                                  │
                          p_knng 子进程（精确 kNN）
                                  │
                           写 .clu 文本文件
                                  │
              读回 + Python 列表解析 + 逐边算 Tanimoto (5.6s)
                                  │
                      scipy 稀疏矩阵对称化 + igraph 建图
                                  │
                              leidenalg (102.7s)
```

CosTaL+（一个进程，相似度矩阵**从不完整存在**）：

```
X ──> 归一化 + 缓存原始范数 ‖·‖
        │
        └─> 分块流水线：对每个 (行块 b × 列块 c) 的小瓦片
              ① BLAS 算出 b×c 的相似度（只有几 MB，待在 cache 里）
              ② 立刻并入每行的 top-k 堆
              ③ 瓦片丢弃 ← 关键：b×N 的大矩阵从未存在过
        │
        └─> k 个幸存者上算 Tanimoto（复用已有的 a·b 和 ‖·‖²）
        │
        └─> 直接吐出对称化后的 CSR 边表
                                  │
                              Leiden
```

省掉的东西，按 docs/02 的数字：文本 IPC 13.4s、Python 边表组装 5.6s、
b×N 的内存往返（这是 top-k 那 88–93% 的真正来源）。

## 2. 为什么 top-k 现在慢，以及怎么让它不慢

这是整个项目最值钱的一处，单独讲。

### 2.1 现状：numpy 的做法

```python
sim = Xn[block] @ Xn.T          # 物化 b×N 的 float32 矩阵
part = np.argpartition(sim, k)  # 对整行 N 个数走一遍 introselect
```

N=265,627 时，一行就是 265,627 个 float32（1 MB），b=256 时是 **272 MB**。
这块内存要**写一遍、再读一遍**，而 M1 Pro 的内存带宽是有限的。
`argpartition` 虽然是 C 实现，但它：

1. **单线程**——8 个核只用 1 个；
2. **要看完整行**——introselect 是 O(N) 但常数不小，且访存模式对 cache 不友好；
3. **额外分配**——返回的是 b×N 的 **int64** 索引数组（265,627×256×8 = 544 MB）。
   本次 profile 就是被这个数组把 16 GB 的机器压进 swap 的。

所以那 88–93% 里，**真正的计算没多少，绝大部分是内存带宽和单线程**。

### 2.2 CosTaL+ 的做法：融合（fused）分块

不物化 b×N，改成对 **(b × c) 的小瓦片**循环：

```
for 行块 B in 0..N step b:            // 可并行，每个线程一个行块
    heaps[b] ← 空的 k 元小顶堆
    for 列块 C in 0..N step c:        // b×c 按每核独占 L2 定，见 docs/06 §2.3
        tile = Xn[B] · Xn[C]ᵀ         // BLAS sgemm，瓦片待在 L2
        for 每一行 i、每个候选 j in tile:
            if tile[i][j] > heaps[i].最小值:   // 绝大多数在这里就被拒了
                heaps[i].替换最小值(j, tile[i][j])
    // 瓦片出作用域即丢弃
```

> **已修订（2026-10-12）。** 原文写的是 b≈256、c≈4096（每线程 4 MB）。
> 这只对 M1 勉强成立：3 个性能核 × 4 MB 正好占满 12 MB 共享 L2，
> 没给列块和堆留位置；在 256 KB L2 的老 x86 上则直接溢出。
> 瓦片尺寸改为"保底值 + 运行时探测"，见 docs/06 §2。
> 另外，每行实际保留 top-(k+m) 交给 f64 精排，保证跨平台结果一致，见 docs/06 §1。

为什么这样快：

- **b×N 不存在了**：峰值内存从 272 MB 掉到一个瓦片（百 KB 到 MB 级，按平台定），
  全程在 cache 里，不吃内存带宽。顺带解决 OOM——**内存不再随 N 增长**。
- **拒绝路径极短**：k=10、N=26 万时，一个候选能进 top-10 的概率约
  10/265627 ≈ 0.004%。也就是说 **99.996% 的候选只要一次浮点比较就被扔掉**，
  分支预测器会学得很准。这比"看完整行再选"便宜一个数量级。
- **天然并行**：行块之间完全独立，8 个核直接开 8 路（rayon）。
  numpy 那条路上，matmul 多线程但 top-k 单线程，这个不对称被消除了。
- **matmul 还是交给现成的矩阵库**（macOS：Accelerate/AMX；其它平台：
  纯 Rust 内核，见 docs/06 §3），我们只写
  ②③ 那两步——这正是 §1.2 说的"这部分自己写才有价值"。

预期收益：把精确 kNN 从「matmul 7–12% + top-k 88–93%」变成
「matmul 占大头 + top-k 边角料」。matmul 那部分已经有 BLAS 兜底，
所以**总时间应该向 profile 里 matmul 那一栏靠拢**
（N=10万：26.6s 而不是 225s）。这是第一阶段要拿的数字。

### 2.3 一个不能搞错的语义细节

**邻居用 cosine 选，边权用 Tanimoto 算，顺序不能反。**

原版就是这么做的：`p_knng` 在 **L2 归一化**的数据上按 cosine 选邻居，
`build_tani_graph` 再用**未归一化**的原始范数算 Tanimoto 边权
（docs/02 §4 已核实）。因为原始范数跨度有 5.8 倍，
**如果把 Tanimoto 塞进 top-k 的比较器里，选出来的邻居集会变**，
就不是 CosTaL 了。所以：

```
top-k 比较器 ── 只看 cosine
     ↓（k 个幸存者）
Tanimoto ── T = d / (‖a‖² + ‖b‖² − d)，其中 d = ‖a‖·‖b‖·cos
```

`‖·‖` 在归一化时顺手缓存，O(N) 一次。这就是 §1.1 说的"复用 a·b 与 ‖·‖²"，
实测占比 1%，确实是边角料。

## 3. 剪枝（p-L2knng）放在哪

§2.2 那套融合分块是**不剪枝的精确解**：老老实实算 N² 个内积。
p-L2knng 的价值是**跳过整批不可能进 top-k 的候选**——用范数上界证明
"这一块里最大的可能内积也够不到当前第 k 名"，于是整块 skip。

架构上的关键判断：

> **剪枝和分块 BLAS 是同一个精确答案的两种候选生成策略。**
> 它们产出完全相同的结果，只是跳过的候选数不同。

所以它们落在**同一个 trait 后面**，而且天然带来一个好用的验证手段：

```
BlockedExact（不剪枝，慢但显然正确）
      ↑ 逐条边比对，必须完全一致
PrunedExact（带剪枝，快）
```

**先做不剪枝的版本**。理由：

1. 它已经能拿到 §2.2 的主要收益（top-k 不再是瓶颈），先把数字落袋；
2. 它是剪枝版的**黄金对照**——剪枝的 bug 全是"漏掉了本该进 top-k 的邻居"，
   这种 bug 不对照根本看不出来，指标只会悄悄变差一点点；
3. 剪枝的收益高度依赖数据分布（维度、稀疏性、范数分布），
   在 Levine_32dim 这种 32 维稠密数据上到底能省多少，**得测了才知道**——
   不能先写完再发现省不了多少。

> **补充（2026-10-12）：L2Knng 本身不适合 Levine。** L2Knng 的剪枝建立在
> 倒排索引上，是为稀疏高维数据设计的；Levine_32dim 全量实测 **100% 稠密**
> （每行 32/32 非零，docs/06 §5.1），倒排索引在这里抓不到东西。
> 所以阶段 D 在 Levine 上的指望只剩 docs/04 §3 的范数窗口（tanimoto）与
> 锥形界（cosine）——两者都是可证明的界，仍然精确。L2Knng 挪到稀疏后端
> （阶段 S，docs/06 §5），只用它的精确模式。

## 4. 分层与 crate 划分

```
costal-core/              纯 Rust，不认识 Python，可单独 cargo test / bench
│
├── prep      归一化 + 范数缓存。输出 (Xn: 行主序 f32, norms: Vec<f32>)
│
├── knn       trait KnnIndex { fn search(&self, k) -> Neighbors }
│             ├── exact::Blocked   §2.2 的融合分块          ← 第一刀
│             ├── exact::Pruned    范数窗口 / 锥形界剪枝    ← 第二刀（docs/04 §3）
│             ├── exact::Sparse    L2Knng 式倒排索引，稀疏输入 ← 阶段 S（docs/06 §5）
│             └── approx::Hnsw     大规模/人脸线，opt-in    ← 后面，永不进默认
│             Neighbors = { idx: Vec<u32>, cos: Vec<f32> }（行主序 N×k）
│
├── weight    cos + norms → Tanimoto / Jaccard / 原始 cosine
│             （融合在 knn 出口，不二次遍历边表）
│
├── graph     对称化 + 去自环 + CSR。对应原版那段 scipy + igraph 胶水
│
└── cluster   Leiden。**第一阶段不做**，见 §5
```

```
costal-py/                只做类型转换和错误映射，不放逻辑
│  暴露给 Python 的东西按"最小可用面"来：
│    build_graph(X, k, method, backend) -> (rows, cols, weights)
│    find_communities(X, ...)           -> labels      ← 等 cluster 层就位
```

### 4.1 为什么 core 和 py 分开

- **能独立跑 benchmark**：`cargo bench` 不需要起 Python 解释器，
  优化 kernel 时反馈循环短得多；
- **C ABI 是顺手的事**（docs/01 §3 第 3 条）：core 已经是纯 Rust，
  再加一个 `costal-c` crate 导出 `extern "C"` 即可，不用重构；
- **绑定层的 bug 和算法的 bug 分得开**。

### 4.2 后端（BLAS / SIMD / GPU）在哪一层

不单独做一层，而是 **knn 层内部的实现细节**：

- `exact::Blocked` 里调用矩阵库的 `sgemm`——Apple 走 Accelerate（自动用 AMX），
  其它平台走纯 Rust 内核，不打包 OpenBLAS/MKL（2026-10-12 改，理由见 docs/06 §3）。
  用 `cfg` 选，对上层透明；
- top-k 合并那一步的 SIMD（NEON/AVX）也在这里；
- Metal/CUDA 将来是**第四个 `KnnIndex` 实现**，不是横切层。
  docs/01 §6 第 2 条那个"Metal 做到什么程度"的问题，
  因为有了 trait 边界，可以先只做 matmul、以后再连 top-k 一起下放，
  不影响其它层。

## 5. Leiden 怎么办（第一阶段：不碰）

docs/02 §3.2 的数字说 Leiden 值得写，但**不是现在**，理由是排序问题：

- 精确路线上 Leiden 只占 10%（1098.7s 里的 102.7s），
  先把 kNN 从 1098.7s 打下来，Leiden 的占比才会浮上来；
- `leidenalg` 是成熟的 C++ 实现，自己写的第一版大概率更慢且结果对不上，
  而"精度不退"是本项目的第一条目标；
- **有一个可能白拿的优化没试**：原版把 `n_iterations` 写死成 10
  （`bc()` 里甚至是 100）。Leiden 论文的建议是迭代到收敛，
  通常 2–3 轮就稳定了。如果 2 轮和 10 轮的划分一致，这里直接省 80%。
  **这是个实验，不是代码工作，应该排在写 Rust Leiden 之前。**

所以第一阶段的交付形态是：

```python
rows, cols, weights = costal_plus.build_graph(X, k=10)   # Rust
G = ig.Graph(...); la.find_partition(G, ...)             # 仍然是 Python
```

这样**一行不写 Leiden 也能拿到完整的端到端加速比**，
而且和原版共用同一个 Leiden 实现，精度对比是干净的
（划分差异只能来自图，不能来自聚类算法）。

## 6. 实施顺序与每一步的验收口径

每一阶段都必须同时给**正确性**和**速度**两个数，缺一不算完。
数据一律是 Levine_32dim（265,627 细胞，带 14 个人工门控标签）。

| 阶段 | 做什么 | 正确性口径 | 速度口径 |
|---|---|---|---|
| **A** | `exact::Blocked` + Tanimoto 融合 + `build_graph` 出边表 | 邻居集与暴力解**逐条相同**（N≤2万全量比对）；端到端 ARI/NMI 与原版 CosTaL 持平 | 对比 docs/02 的 1098.7s（N=26万）。目标：向 matmul 那一栏靠拢 |
| **B** | `graph` 层进 Rust（对称化 + CSR） | 边表与 A 阶段 + scipy 的结果一致 | 吃掉 docs/02 的 5.6s |
| **C** | Leiden `n_iterations` 实验 | 2/3/5/10 轮的划分 ARI 互比 | 若 2 轮够，省下 102.7s 的 ~80% |
| **D** | `exact::Pruned`（范数窗口 / 锥形界，docs/04 §3） | **与 A 阶段逐条相同**（这是硬门槛） | 相对 A 的加速比；若 <1.5× 就不值得留 |
| **E** | `approx::Hnsw` 进 trait（opt-in，永不进默认） | 召回率 vs A；ARI 掉多少 | 给大规模/人脸线用 |
| **F** | Metal / CUDA 后端 | 同 A | 视 A 之后 matmul 占比决定要不要做 |
| **S** | `exact::Sparse`（L2Knng 式，精确模式），之后再做 `backend="auto"` | 与暴力解逐条相同 | 基因级 scRNA-seq 上相对 A 的加速比 |

> **C 排在 D 前面**是故意的：C 是个实验（几小时），D 是真正的工程（几天）。
> 先把便宜的收益拿掉，再看贵的还值不值得做。
>
> **2026-10-12**：A 阶段从第一天带上 f64 精排与跨平台的瓦片策略；
> 新增阶段 S（稀疏后端）。细节见 docs/06 §7。

### 6.1 不做什么（避免范围蔓延）

- **不碰 `pp` 预处理**：实测 0.23s，占比 0%。保持 Python 侧即可。
- **不自己写 BLAS**：matmul 只占精确 kNN 的 7–12%。macOS 用 Accelerate，
  其它平台用现成的纯 Rust 内核（docs/06 §3），也不打包 OpenBLAS/MKL。
- **不做降维**（docs/01 §6 第 4 条）：PCA 会改变相似度语义，
  在"精度不退"这条目标定下来之前不进默认管线。

## 8. 阶段 A 结果（2026-10-12）

> 环境：M1 Pro（6 个性能核 + 2 个能效核，16 GB），macOS 26.5.2，原生 arm64 的 Python 3.9.6，
> matmul 用 Accelerate。测试期间 swap 已用 8.4 GB，绝对秒数偏保守。
> 命令与原始数字：`bench/stage_a.py`、`bench/out/stage_a.json`。结果由提交 36140df 的代码产生
> （扩展是在版本号改成 0.1.0 之前构建的，json 里的版本字段因此记作 0.0.1，代码相同）。

### 8.1 正确性

| 检查 | 结果 |
|---|---|
| 与 Rust 的 f64 暴力解比对（Levine 子集 N = 10k、20k） | **逐位相同**（邻居与 cosine） |
| 合成数据：瓦片尺寸 × matmul 后端 × 布局 × 线程数 | 全部逐位相同（`cargo test`、`pytest`） |
| 大量精确并列（整数数据、重复行、零行） | 逐位相同，靠下面的兜底 |
| Tanimoto / Jaccard / 模糊并集 vs 原版代码 | 逐位相同（`tests/test_knn.py`） |
| 与原版 `bc()` 路径对照（去重的 Levine，N = 50k） | 邻居集 **100% 相同**；边数相同（401,424）；Tanimoto 最大相对差 6e-8（我们的输入是 f32） |
| 同上，Leiden 划分（5 个 seed） | 同 seed 下两边划分 **ARI = 1.0（5 个 seed 全部）**；对门控标签两边都是 ARI 0.804 ± 0.073、NMI 0.875 ± 0.026 |

Leiden 自己换 seed 的一致度只有 ARI 0.833——**同一张图上 Leiden 的随机性，比两种实现之间的
差别大得多**（后者为零）。单个 seed 的精度数字不能拿来比较方法。

**一个相对 docs/06 §1.2 的设计修正**：只靠余量 m 不够。大量精确并列时，第 k 名处的并列组可以比
k+m 还大，粗选的同分取舍就可能丢掉按原始索引该赢的那个（整数测试数据上实际发生了）。现在改成
可证明的界：没进堆的候选，真实 cosine 不超过堆根 + ε（ε = (d+4)·2⁻²³）；第 k 名严格高于这个界
⇒ 精确，否则该行整行收集再精排。**Levine 上所有规模的兜底次数都是 0**。

### 8.2 速度（未去重的原始文件，规模与 docs/02 对齐）

| N | 精确 kNN | 边权 + 对称化 | docs/02 对照 |
|---:|---:|---:|---|
| 10,000 | 0.022 s | 0.001 s | 分块 BLAS 2.15 s；phenograph 22.6 s |
| 50,000 | 0.31 s | 0.006 s | 分块 BLAS 40.7 s；phenograph 75.0 s |
| 100,000 | 1.02 s | 0.017 s | numpy matmul 单独 26.6 s（本阶段原定"向它靠拢"的目标） |
| 265,627 | **6.47 s** | 0.043 s | 分块 BLAS **1098.7 s**（≈170×） |

- 原版的写 `.ijv` + 解析 `.clu` + 组图（S1 + S3，全量 17.0 s）现在是 43 ms。
- 去重 Levine 50k 上：原版 `bc()` 建图 29.0 s（其中 phenograph 28.0 s），CosTaL+ 0.35 s。
- **瓶颈已经换成 Leiden**：全量 265,627 行建图 7.6 s、Leiden 112 s；去重后 161,443 个细胞
  建图 3.0 s、Leiden 69 s。**阶段 C（`n_iterations` 实验）现在是最值钱的下一步。**

### 8.3 瓦片与 matmul 后端（N = 50k 扫描，验证 docs/06 §2–§3）

- Accelerate 比纯 Rust 的 `gemm` 快约 2.2×（各自最佳瓦片下 0.43 s vs 0.93 s）。
- 瓦片 128 KB–2 MB 之间是平台区（差距 < 15%）；≤ 64 KB 明显变慢（每次 matmul 调用的固定开销）。
- 按缓存推出的默认值（每线程 L2 4 MB → 瓦片 2 MB，512 行 × 1024 列）是扫描里最快的一档：0.42 s。
- 每个候选的综合成本约 3 个周期（含 matmul；按 8 核、3.2 GHz 粗算）。matmul 与扫描各占多少
  **没拆开测**，docs/04 §1 的"约 1 周期/候选"仍是估算。

### 8.4 Levine_32dim 的重复细胞（docs/02 附记）

上游文件里每个已门控细胞出现两次（104,184 对），真实细胞数是 161,443。

- 原版 `bc()` 的 `idx[:, 1:]` 在重复细胞上会失效（docs/04 §4 第 4 条）；未去重时与原版的差异
  全部来自这一点和复制品之间的精确并列，**没有一行是真实的邻居差异**。
- **重复会抬高精度评估**（全量、CosTaL 默认参数、5 个 Leiden seed）：

| 数据 | 细胞数 | ARI（对门控标签） | NMI |
|---|---:|---:|---:|
| 去重 | 161,443 | 0.766 ± 0.008 | 0.860 ± 0.004 |
| 原始文件（含重复） | 265,627 | 0.861 ± 0.029 | 0.880 ± 0.015 |

ARI 被抬高约 0.095，远超 seed 间的波动。合理的解释是：被评分的恰好是那些被复制的细胞，它们所在
群体的密度被翻倍了。**这里只测了 CosTaL 一个方法**；其它方法在这份文件上是否同样被抬高、排名是否
会变，没有测。此后 CosTaL+ 的精度评估一律用去重数据（docs/02 附记）。

# 跨平台、确定性与后端选择（v0，2026-10-12）

> 前情：docs/03 的融合分块是对着一台 M1 Pro 想的，但交付面是
> macOS / Linux / Windows、桌面和服务器（docs/01 §3）。几类机器的缓存结构、
> 矩阵库、核心类型都不一样。本文回答：**同一份代码，怎么在每个平台上都快，
> 而且在每个平台上给出同一个答案。**
>
> 顺序是故意的：**先保证答案一致（§1），再谈快（§2–§4）**。§1 做对了，
> 后面所有调优都只影响速度，不影响输出。

> **精确性声明**：本文所有手段都不改变"精确 kNN"。要么逐对全算（§1–§4），
> 要么只跳过**可证明**进不了前 k 的候选（docs/04 §2–§3 的保守阈值与剪枝、
> §5 的 L2Knng 精确模式）。近似方法（HNSW，docs/03 阶段 E）只作 opt-in，
> **永不进默认路径**——默认路径不精确，就不是 CosTaL。

## 1. 结果一致性：f32 全量粗选 + f64 精排

### 1.1 问题

- matmul 用 f32（docs/04 §4.1）。不同矩阵库（Accelerate / OpenBLAS / MKL /
  纯 Rust 内核）累加顺序和 FMA 用法不同，舍入就不同；同一个库在不同瓦片形状、
  不同指令集上也可能不同。
- 第 k 名附近的"几乎并列"会因此翻转 ⇒ **同一份数据在 Mac 和 Linux 上建出
  两张略有不同的图**。docs/04 §4.1 的 tie-break 只能处理**精确相等**，
  处理不了"舍入导致的顺序翻转"。
- 更麻烦的是：瓦片尺寸（§2）、线程数、后端（§5）一变，结果也可能变——
  **调优和正确性缠在一起**，每调一次都得重新验一遍正确性。

### 1.2 做法

```
f32 全量粗选：分块 matmul 仍然逐对计算全部 N² 个相似度，
              但每行保留 top-(k+m)，m 是余量（初定 m = k）
     ↓ 每行 k+m 个候选
f64 精排：对这 k+m 个候选，用 f64、按维度下标的固定顺序重算 a·b
     ↓
按 f64 值取前 k；相等时取原始索引较小者（docs/04 §4.1）
```

"粗选"指的是**精度**粗（f32），不是**范围**粗：全部候选都算过，没有近似。

- **为什么这能跨平台一致**：f64 精排是一段普通的 Rust 循环。Rust 默认
  **不做浮点收缩**（不会擅自把乘、加合成 FMA），没有 fast-math 也不会重排
  浮点累加，所以同一段代码在 x86 和 ARM 上逐位相同。
- **代价**：`N·(k+m)·d` 次 f64 乘加。全量 Levine：265,627 × 20 × 32 ≈ 1.7 亿次，
  毫秒级。
- **剩余风险**：真实的第 k 名在 f32 下掉到了 k+m 名之外。这要求 m 个候选的
  f32 误差同时朝一个方向偏，**用测试量化，不靠信念**：L2 暴力对照里统计
  "粗选漏选"次数，期望恒为 0。
- 边权也用精排后的 f64 cos 算（输出时再转 f32），所以 Tanimoto 边权同样跨平台一致。

### 1.3 它解锁了什么

- §2 的瓦片尺寸、§3 的矩阵库、线程数、§5 的稠密/稀疏后端，**都不再影响输出**，
  可以放心按平台调。
- docs/04 §4 的 L1/L2 正确性网可以在 CI 的三个系统上都要求**逐条相同**，
  并新增一项：**三个平台的输出互相逐条比对**。
- docs/04 §6.1 的 `truncate()` 成立：精排后每行按 (f64 相似度降序, 原始索引升序)
  全序排好，前缀就是更小 k 的精确答案。
- L3（与原版 `p_knng` 对照）仍然只能做到"除近似并列外相同"：`p_knng`
  有它自己的精度和累加顺序。这道缝有多大，要用黄金输出量（docs/04 §4）。

## 2. 缓存与瓦片尺寸

### 2.1 为什么 d=32 时缓存比算力重要

全量 N=265,627：候选对 N² ≈ 7.06×10¹⁰ 个。每个相似度由 matmul 写 4 字节、
再被 top-k 读 4 字节。

- 瓦片若**溢出到内存**：要搬 ≈ 565 GB，按 M1 Pro 约 200 GB/s 算 ≈ 3 s，
  与计算本身同量级；
- 瓦片若**留在缓存里**：这笔搬运基本消失。

d 越小，每个相似度的计算越少（d=32 时只有 32 次乘加），搬运的占比就越高。

> 以上是**估算，未实测**。阶段 A 的 bench 要给出真实数字。

### 2.2 各平台的缓存结构

| 平台 | 每核 L1D | L2 | L3 |
|---|---|---|---|
| M1 Pro（本机，`sysctl` 实测） | 128 KB（性能核） | 12 MB，3 个性能核共享（共两组） | `sysctl` 不报告 L3；另有系统级缓存 SLC（评测约 24 MB，CPU/GPU 共用） |
| 桌面 x86（Windows 常见） | 32–48 KB | 每核独占：2015–2020 年 Intel 256 KB，新的 1–2 MB；AMD Zen 2/3 512 KB，Zen 4 1 MB | 十几到几十 MB，全核共享 |
| 服务器 x86（Linux 常见） | 32–48 KB | 每核独占 512 KB–2 MB | 很大，但几十个核分；AMD 按 CCD（8 核）切开 |

> 第二、三行是典型值，具体型号会有出入。

### 2.3 原则：瞄准"每核独占的那份"，L3 只当兜底

- **不瞄准 L3**：L3 被所有核共享，服务器上还有别人的进程，能分到多少不可预测。
- **瞄准每核独占的 L2**：每个线程的工作集（瓦片 + 列块 + 堆）按它来定。
- **docs/03 §2.2 原来的 256×4096（每线程 4 MB）作废**：在 M1 上 3 个性能核 × 4 MB
  正好占满 12 MB 共享 L2，没给列块和堆留位置；在 256 KB L2 的老 x86 上直接溢出。

三层：

1. **保底值**：按常见的最小独占 L2（256 KB）的一半定瓦片，≈128 KB
   （如 32×1024 个 f32）。不是最优，但在任何平台上都不会溢出到内存。
2. **运行时探测**：Linux 读 `/sys/devices/system/cpu/cpu*/cache/`，macOS 读
   `sysctl hw.perflevel*`，Windows 调 `GetLogicalProcessorInformationEx`；
   按"每线程分到的 L2"放大瓦片（M1：12 MB / 3 核 = 4 MB，瓦片取一半）。
   读不到就用保底值。
3. **（可选）首次运行自测**：试 3 个尺寸、各约 30 ms，结果存在本地，
   之后直接用（FFTW 的 wisdom 思路）。

因为 §1，这三层只影响速度，不影响输出。

### 2.4 备选：寄存器级融合（阶段 A 不预设）

另一条路是根本不让瓦片落地：在 SIMD 寄存器里算完点积，直接和阈值比较。
工作集只剩几 KB，彻底不依赖缓存大小。代价是要为 NEON / AVX2 / AVX-512
各写一份微内核，而且在 Mac 上用不到 AMX（AMX 只能经 Accelerate 调用）。
**阶段 A 先做 BLAS + 瓦片，bench 之后再决定要不要走这条。**

## 3. 矩阵库

| 平台 | 用什么 | 理由 |
|---|---|---|
| macOS | Accelerate（系统自带，走 AMX） | 零依赖，且最快 |
| Linux / Windows | 纯 Rust 矩阵内核，候选 `gemm` crate | 运行时自动选 AVX2 / AVX-512 / NEON，不依赖任何外部库 |

- **不打包 OpenBLAS / MKL**：要把它们塞进 manylinux / musllinux / Windows wheel，
  还要处理线程超订（和用户进程里 numpy 自带的那份 OpenBLAS 抢核），
  工程代价远大于收益。
- d=32 时 matmul 只占精确 kNN 的 7–12%（docs/02 §3.3），纯 Rust 内核足够。
  **先 bench 再定。**
- `gemm` crate：crates.io 0.19.0（2025-11），candle、faer 都依赖它（2026-10-12 查得）。

## 4. 并发细节

1. **大小核 → 工作窃取。** Apple（P 核 + E 核）、Intel 12 代以后（包括 NAS 的
   Pentium Gold 8505）都是大小核。平均分活会让快核干等慢核 ⇒ 行块切小，
   用 rayon 的工作窃取。
2. **缓存行 → 统一按 128 字节对齐。** Apple 是 128 字节（本机
   `sysctl hw.cachelinesize` = 128），x86 是 64 字节。每线程的堆、阈值等
   **可写**状态统一按 128 字节对齐（如 `crossbeam_utils::CachePadded`），
   防止两个线程改同一缓存行（伪共享）。x86 上只多占一点空间。
3. **对称性 → matmul 减半（实验项）。** cos(i,j) = cos(j,i)：只算上三角瓦片，
   一个值同时喂给第 i 行和第 j 行的堆。第 j 行的堆可能属于别的线程 ⇒
   每线程先写本地缓冲，最后合并。合并结果由 §1 的精排和原始索引 tie-break 决定，
   与线程数无关。收益和合并开销都要测。
4. **NUMA（双路服务器）：影响小，不专门处理。** 输入 X 只有 34 MB 且只读；
   每线程的堆由自己分配（首次写入时落在本地内存）。

## 5. 稠密 / 稀疏两条后端与 `backend="auto"`

### 5.1 两类数据

Levine_32dim 实测（2026-10-12，全量 265,627 细胞，`arcsinh(x/5)` 之后）：
**非零比例 1.000**（每行 32/32 非零）；**27.0% 的元素为负**，99.8% 的行含负值，
最小约 −0.058。

| 数据 | 例子 | 后端 |
|---|---|---|
| 低维稠密 | CyTOF / 流式（Levine：32 维，没有零）；先验知识投影（通路 / TF 活性、基因程序，§5.3） | 分块 matmul + top-k（阶段 A） |
| 高维稀疏 | 基因级 scRNA-seq（原版 `pp(..., 'scrnaseq')`：2000 个高变基因、log1p、稀疏 CSR） | L2Knng 式倒排索引 + 剪枝（阶段 S，**只用精确模式**） |

L2Knng 的剪枝建立在倒排索引上，是为稀疏高维数据设计的（docs/02 §1.1 附记）。
在 32 维全稠密数据上，每条倒排链都有 N 个元素，剪枝省下的只是 32 次乘加里的
一部分，打不过 BLAS 瓦片——**这是判断，不是测量**。

### 5.2 auto 分派的三条约束

1. **阈值要测。** 稀疏划不划算，取决于零的比例**和**维度。分界点只能等两条后端
   都写好后，在同一批数据上测出来 ⇒ `auto` 排在阶段 S 之后。
2. **分派必须确定、可见、可覆盖。** 规则只看输入本身（是否稀疏格式、非零比例、维度），
   同一输入永远走同一后端；实际走了哪条写进输出元数据；`backend="dense"` /
   `"sparse"` 可以强制指定。两条后端**共用 §1 的同一个 f64 精排**，所以只要候选池
   都包含真正的前 k，输出逐条相同，分派只影响速度。
3. **`compat="paper"` 单独对待。** 原版不分数据，一律走 `p_knng`。我们的输出与
   `p_knng` 的差异只可能出在近似并列上（§1.3），差多少等黄金输出量化。

### 5.3 先验知识投影：把基因投到"有生物学意义的东西"上

> 2026-10-12 按调研改写。初稿写的是"以功能单元为单位"，更准确的说法是：
> **拿先验知识定义的生物学实体（信号通路、转录因子调控子、基因程序）当坐标轴，
> 把每个细胞的基因表达投射过去**，在这个空间里描述细胞状态。

三类做法：

| 类别 | 代表 | 怎么投 | 输出维度 |
|---|---|---|---|
| 活性推断（线性投影） | PROGENy（信号通路）、CollecTRI（TF 调控子），经 decoupler 计算；AUCell / ssGSEA（基因集评分） | 先验权重矩阵 × 表达量（PROGENy 就是一次矩阵乘） | PROGENy 14 条通路；CollecTRI 覆盖 1,186 个 TF（43,175 条带符号的调控关系）；基因集可到上千 |
| 先验约束的隐空间 | VEGA、expiMap（VAE，解码器按基因程序连线）；Spectra（矩阵分解，已知基因集 + 新发现的程序） | 学出来，但每一维对应一个已知程序 | 程序个数，通常几百 |
| 每个程序一个嵌入 | Tripso（自监督 transformer，bioRxiv 2026-03） | 每个细胞、每个程序各一个向量 | 一个细胞是**一组**向量，不是一个 |

**还是稀疏的吗？不是。** 输入的基因矩阵仍然稀疏，但投射之后的"细胞 × 实体"矩阵
是**低到中维、稠密**的：每个分数汇总几十到几百个基因，单个基因测不到留下的零被
平均掉了。AUCell 对小基因集、Spectra 这类非负分解的打分可能出现不少零，但维度本身
就低，仍然走稠密后端。

对 CosTaL 的含义（**判断，待实测**）：

1. **幅度有信息。** 活性分数的大小就是活性强弱，没有被归一化抹平——正好是 Tanimoto
   精修起作用的那一侧（docs/01 §7），这类表示可能是 CosTaL 很自然的输入。例外是
   按细胞归一到和为 1 的程序用量（如 cNMF 的归一化用量），幅度信息被部分抹掉。
2. **有正有负。** PROGENy、CollecTRI 的活性分数带符号；docs/04 §2.4 修订后的护栏
   不依赖输入符号，能跑。
3. **维度跨度大。** 14 维时和 CyTOF 一样是低维稠密；到上千维时，matmul 在精确 kNN 里
   的占比会明显上升（docs/05 §4.1 第 5 条），那时 GPU 的讨论才有意义。
4. **"一个细胞多个向量"不直接适配现在的 kNN。** Tripso 这类表示可以每个程序各建一张
   kNN 图、再做多层（multiplex）Leiden（`leidenalg` 支持多层图优化），也可以拼接成
   一个向量。这是新的设计问题，**待定，不预设**。
5. 与 docs/05 §4.2 一致：这些都是**可选的输入表示**，不进默认路径。默认路径仍是
   "对用户给的矩阵做精确 kNN"。

## 6. 不走的路

- **TypeScript / WebGPU**：TS 碰 GPU 只能走 WebGPU，在 Mac 上最终也翻译成 Metal
  （Deno 的 WebGPU 底层就是 Rust 的 `wgpu`）。Rust 可以直接用 `wgpu` 或 Metal，
  少一层；而引入 JS 运行时，与"`pip install` 之后离线可用"冲突。将来若做浏览器端
  可视化（如 nas-manager 的界面），那是前端产品，不是加速路线。
- **反编译 `p_knng`（REA / Ghidra 之类）**：源码可读、二进制没 strip，我们缺的是
  黄金输出，靠运行拿，不靠反编译。见 docs/02 §1.1 附记。
- **名词澄清**：**Metal** 是苹果的 GPU 编程接口（对标 NVIDIA 的 CUDA），只在苹果
  设备上有；**Accelerate / AMX** 是 CPU 侧的矩阵协处理器，不是 GPU。
  GPU 后端仍是 docs/03 的阶段 F。
